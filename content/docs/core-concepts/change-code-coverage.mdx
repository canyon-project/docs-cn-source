# 变更代码覆盖率（Change Coverage）计算标准 — Canyon

**目标读者**：前端开发者、测试工程师、CI/DevOps。
**目的**：定义 Canyon 对「变更代码覆盖率」的明确计算标准，用于评估一次变更（从 `base` 到 `head`）中新增加代码的测试覆盖情况，并指导 CI 校验与报告展示。

---

## 一、概述（Why）

变更代码覆盖率衡量的是本次变更中新增加代码在测试（单元 / E2E / 集成）下被执行的比例。不同于仓库整体覆盖率，变更覆盖率聚焦 **“本次改动新增的可执行代码”**，能更直接反映变更风险与测试有效性，从而用于 MR 质量门控、review 指标与回归风险评估。

---

## 二、数据源（Data Sources）

1. **代码变更（diff）**

   * 数据来源：Git 两个提交（`base` → `head`）之间的差异（`git diff` 或 CI 的合并变更范围）。
   * 我们只关心 **新增（added）行**，即 diff 中以 `+` 标记的行（不包含上下文与删除行）。
   * 对象范围：每个变更文件（通常只考虑源码文件，如 `.js`, `.ts`, `.jsx`, `.tsx` 等）。

2. **覆盖率数据（coverage）**

   * 数据来源：测试运行后导出的 Istanbul 风格覆盖率 JSON（例如 `nyc`/`istanbul` 输出），或等价结构。
   * 我们只关注 **“语句（statements）”** 维度（Statement-level coverage）。理由见后文。

> 前提：覆盖率数据需要能够映射到**源码行号**（即插桩/构建阶段应保持 source-map 或直接对源码插桩），否则无法准确把新增行归属到语句范围。

---

## 三、定义（Definitions）

* **新增代码行集合 `L_f`（for file f）**：在 `file f` 从 `base` 到 `head` 中被新增的行号集合（相对于文件在 `head` 的行号空间）。

* **文件语句集合 `S_f`**：由覆盖率数据中 `statementMap` 给出的所有语句范围（每个语句为一段行区间，含起始行与结束行）。语句通常带有一个 id（statementId）；对应的执行次数由 `s[statementId]` 给出。

* **落到语句范围的语句（impacted statements）`I_f`**：对于文件 `f`，所有满足 `statementRange ∩ L_f ≠ ∅` 的语句集合。即：任何新增行落入该语句的行区间，则该语句被认为“影响到本次变更”。

* **已覆盖的影响语句集合 `C_f`**：在 `I_f` 中，执行次数 > 0（或定义为被覆盖）的语句集合。


* **变更代码覆盖率（文件级）**：

### 文件级变更覆盖率计算

```math
coverage_f = \begin{cases} \dfrac{|C_f|}{|I_f|} & \text{if } |I_f| > 0 \\ \text{无新增可执行语句（见策略）} & \text{if } |I_f| = 0 \end{cases}
```

### 总体变更覆盖率计算

```math
coverage_{change} = \dfrac{\sum_f |C_f|}{\sum_f |I_f|} \quad (\text{仅当 } \sum_f |I_f| > 0)
```


---

## 四、详细计算逻辑（Step-by-step）

**输入**：`base` commit、`head` commit、coverage JSON（基于 `head` 的源码行号）
**输出**：每个变更文件的变更覆盖率，以及合并后的变更覆盖率

1. **获取变更文件与新增行**

   * 使用 `git diff --unified=0 base..head -- <file>` 或 CI 提供的 changed-files 接口。
   * 从 diff 中解析所有新增行段（hunk header `@@ -a,b +c,d @@`，新增行从 `c` 开始，长度为 `d`，或以 `+` 行前缀收集行号）。
   * 结果：对每个文件 `f`，得到新增行号集合 `L_f = {l1, l2, ...}`。

2. **加载文件的覆盖率信息**（Istanbul JSON）

   * coverage[filePath] 包含 `statementMap`（语句范围）与 `s`（语句执行次数）。
   * `statementMap`：例如 `{ "1": { "start": {line, column}, "end": {line, column} }, ... }`
   * `s`：例如 `{ "1": 0, "2": 3, ... }`。

3. **计算 impacted statements `I_f`**

   * 对每个 `statementId`，取其行区间 `[start.line, end.line]`。
   * 如果该区间与 `L_f` 有交集（存在 l ∈ L_f 使得 start.line ≤ l ≤ end.line），则把该 `statementId` 加入 `I_f`。

4. **判定覆盖**

   * 对 `I_f` 中每个 `statementId`，若 `s[statementId] > 0` 则认为该语句被覆盖，加入 `C_f`。

5. **计算文件级和合并覆盖率**

   * 文件级：`coverage_f = |C_f| / |I_f|`（若分母为 0，见策略）
   * 全量：合并分子与分母求比。

6. **输出结果与字段**

   * 每个文件：`{ file, impacted_statements: |I_f|, covered_statements: |C_f|, coverage: coverage_f }`
   * 合并：`{ total_impacted: Σ|I_f|, total_covered: Σ|C_f|, change_coverage: Σ|C_f|/Σ|I_f| }`

---

## 五、示例（示意）

假设文件 `foo.js` 的覆盖率中有 3 个语句：

* stmt1: lines 1–3, execCount = 2
* stmt2: lines 4–6, execCount = 0
* stmt3: lines 7–10, execCount = 1

`git diff` 发现新增行集合 `L_foo = {2, 5}`，则：

* stmt1 intersects line 2 → impacted
* stmt2 intersects line 5 → impacted
* stmt3 不受影响

于是 `I_foo = {stmt1, stmt2}`，`C_foo = {stmt1}`（因为 stmt2 执行次数 0）

文件级 coverage: `coverage_foo = 1 / 2 = 50%`

若这是唯一变更文件，则 `change_coverage = 50%`

## 七、边界情况与策略（Important rules）

1. **文件无覆盖率数据（coverageJson 没有该文件）**

   * 可能原因：文件未被插桩（未包含在测试构建中）、生成文件、或路径不匹配。
   * 策略建议：标记为 `no coverage data` 并在报告中突出（不计入分母，或按项目策略决定是否作为失败条件）。

2. **分母为 0（|I_f| = 0）——“无新增可执行语句”**

   * 情况：新增的只是注释、空行、非 JS 资源，或者插桩器把新增行判为不可执行行。
   * 策略推荐（两种常见做法，团队需选一并一致执行）：

     * **默认不参与（推荐）**：将其从合并分母中排除，并在报告中显示为 *无新增可执行语句*。理由：无法从测试覆盖率角度评估代码，因为没有可执行语句。
     * **视为 100% 覆盖（不推荐）**：可能掩盖无测试的新增功能，风险较高。仅在某些保守场景可选。

3. **重命名 / 移动文件**

   * 使用 `git diff --find-renames` 或 CI 的 changed-files 接口以识别重命名，确保行号对齐到 `head` 版本。
   * 若行号映射复杂，最好把重命名视为“新文件”来处理（并按策略 1 处理 coverage 缺失）。

4. **新增行位于语句中间（语句跨多行）**

   * 仍按“交集”逻辑处理：只要新增行落在语句范围内，该语句计入 `I_f`。这能覆盖常见的多行表达式、函数体等。

5. **生成文件 / 第三方依赖**

   * 通常在 diff 时排除 `dist/`, `node_modules/`, 以及其他生成产物。

6. **测试来源为 E2E（浏览器覆盖）时的行号一致性**

   * 确保插桩阶段是对源码插桩（或使用 source-map 恢复到源码），否则 coverage 的 statementMap 将对应打包后的代码行，导致交集判断失效。

## 九、展示与可视化建议

在 Canyon 项目页面和 MR 中建议显示：

* **总体变更覆盖率**（百分比）和分级颜色（绿/黄/红）
* **文件级列表**：每个变更文件的 `impacted / covered / coverage`，并提供展开查看具体 impacted 语句（带行号）及执行次数。
* **未覆盖语句明细**：点击可展示相关代码片段与新增行高亮，便于 reviewer 定位缺失测试。
* **时间序列**：展示同一分支 / 同一文件随后迭代的变更覆盖率趋势（帮助判断是否稳定上升/下降）。

## 十、为什么只关注“语句”维度（Design rationale）

* **语句（statement）级能兼顾精度与稳定性**：比行级更能包容表达式跨行、自动格式化差异，比分支级更直接且更易计算。
* **分支/函数级虽然有价值，但映射复杂度更高**（例如某些语句包含多个分支），且对于快速判断变更是否被测试，语句级已足够敏感。
* 因此 Canyon 把“语句级”作为变更覆盖率的标准粒度，分支/函数级可作为补充指标。

---

## 十一、性能与扩展性考虑

1. **大 PR（百万行）**：解析 diff 与遍历 statementMap 的复杂度与变更行数成正比，通常可在几十秒内完成；若非常大，建议分片或只统计前 N 个文件。
2. **缓存**：在 CI 中可缓存 coverage JSON（若并行测试）以减小 I/O 开销。
3. **并行化**：文件级计算可并行，最终合并分子与分母。
4. **容错**：遇到文件路径不匹配、缺失 coverage 时，应返回可解释的警告，而非直接失败（除非团队策略要求严格 fail）。

## 十三、限制与假设（请注意）

* 该方法依赖 `coverage` 的 `statementMap` 能够反应源码行号；若 coverage 是针对打包后代码且未映射回源码，将导致错误结果。
* 对于极端代码生成场景（例如运行时动态拼接 JS），语句范围可能不会匹配，需额外策略。
* 因为只计算“新增行落到的语句”，若变更是重构（移动/拆分语句但逻辑未变），结果可能会产生噪声 —— 推荐结合 MR 类型（修复/重构/文档）做额外标注。

---

## 十四、推荐实践（Summary）

1. 在测试构建中保证 **对源码插桩或生成能映射到源码的 coverage**（source-map 支持）。
2. 使用上述交集方法计算每个变更文件的 impacted statements 并求覆盖率。
3. 对 `|I_f| = 0` 的文件做**特殊标注并从合并中排除**（更清晰且更公平）。
4. 在 CI 中把变更覆盖率作为 MR 报告或门控指标，阈值与报警策略由团队制定。
5. 在 Canyon UI 中展示未覆盖语句的行号与代码片段，便于快速补测或 reviewer 指导。
