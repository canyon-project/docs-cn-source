# 跨不同提交合并代码覆盖率

目前，大多数项目的端到端测试仍以手动为主，UI自动化使用率较低。在这种情况下，一个Merge Request通常包含多个提交，每个提交对应一个测试覆盖率数据。

Canyon当前的覆盖率数据是按提交聚合的，无法全面反映整个MR的测试覆盖情况。为了减少回归测试工作量并提高测试效率，我们希望支持按Merge Request ID聚合覆盖率数据。

> [!IMPORTANT]
>
> 当使用合并功能时，可能会出现以下问题：
> 1. 合并的最小维度是语句块。
> 2. 当a.ts中的某个语句在commit1中被覆盖，但在commit2中被删除，最终版本仍恢复a.ts时，该语句的实际覆盖率为0。但如果在这里合并，覆盖率将显示为100%。

## 快速概览

- **MR级聚合**：以head commit为基线，聚合多个提交的覆盖率。
- **fileMerge**：文件级合并；对未变更文件累加计数。
- **blockMerge**：先进行文件级合并，**然后按代码块合并变更文件**。
- **实践建议**：默认使用**fileMerge**；当需要变更文件的块级命中时，使用**blockMerge**。

## 解决方案

### 文件合并

- **fileMerge**：以MR的head commit为基线，合并所有提交的覆盖率数据
  - 对于未变更文件，直接累加命中计数
  - 对于变更文件，保持基线文件的覆盖率数据不变（**不进行块级合并**）

### 代码块合并

- **blockMerge**：以MR的head commit为基线，合并所有提交的覆盖率数据（先按文件合并，然后按语句代码块合并变更文件）
  - 对于未变更文件，直接累加命中计数
  - 对于变更文件，执行块级合并：
    - 基线文件的语句代码块保持不变
    - 其他提交中与基线语句代码块位置相同的块，如果被命中，则累加计数
    - 合并过程中如果有多个相同的代码块，不进行合并

### 选择指南

- **默认**：优先选择`fileMerge`，简单且风险低。
- **细粒度统计**：选择`blockMerge`对变更文件进行块级合并处理。

## 流程

1. **HTTP GET /api/coverage/map** - 接收请求并解析subject参数
2. **根据subject类型处理**：
   - 如果是commit，查询并聚合单个提交的覆盖率数据
   - 如果是pull，执行MR覆盖率合并
3. **MR覆盖率合并流程**：
   - 解析head和所有相关提交
   - 查询并聚合每个提交的覆盖率数据
   - 根据合并模式执行合并：
     - fileMerge：按文件合并，对未变更文件累加计数
     - blockMerge：先按文件合并，然后对变更文件按代码块合并
4. **返回JSON结果**
